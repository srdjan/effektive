What Effektive is

Effektive is a small functional language designed to transpile to Effect-TS.

Effektive combines immutable data, arrow functions, pattern matching, and typed service operations. A program reads like direct TypeScript, while each function contract records expected failures and required capabilities.

The transpiler turns each contract into an Effect-TS type. A function that returns A, fails with E, and uses R becomes Effect.Effect<A, E, R>.

Services become Context services, and providers become Layer values. Records, types with identity, and errors become Schema declarations. Options become Option values.

The transpiler targets the effect core modules and selected modules from the Effect ecosystem. The table names each module and its role.

Effect-TS moduleRole in transpiled code
effect: Effect, Context, Layer, Option, SchemaComputations, services, providers, options, records, types with identity, and errors. The examples use these modules now.
effect/http, FileSystem, and @effect/platform-node, -bun, or -browserHTTP and file services, and the runtime for each host.
effect/sql and a driver such as @effect/sql-pgDatabase services.
@effect/opentelemetryExport of traces, metrics, and logs.

Version 0 specifies the core mapping. Bindings for the HTTP, file, SQL, and telemetry modules need later specifications. A typed host module will expose them as Effektive services.

Version 0 has a Deno transpiler and CLI in the effektive-lang repository. The Effect-TS examples in this book are manually written for Effect 4.0.5, the Effect library for TypeScript. This site does not run Effektive code.

The transpiler boundary is a typed intermediate representation, or IR. Each expression records its type, execution mode, failures, requirements, and source position. The Effect-TS backend translates checked IR into TypeScript.

Implemented core 0Core 1 design or later
Immutable records, arrays, options, and types with identityMacros and recursive schemas
Functions, pipelines, match, and typed catchUser generics and provider construction
Services, retry, providers, and modulesArbitrary JavaScript and Promise interoperation

Effektive separates domain failures from defects and cancellation. A missing user can be data. Invalid safe-integer arithmetic is a defect. A typed catch handles only declared domain failures.

Three facts describe each function call. The result type describes normal completion. The failure set names expected errors. The requirement set names service methods.

These facts travel through composition. A caller must account for expected failures and required capabilities. Execution mode separately records whether invocation performs effects.

This book first explains values and contracts. It then develops one Users service across lookup, update, recovery, retry, and provision. A payment pipeline joins the concepts near the end.

Values and types

Every Effektive binding and aggregate value is immutable.

This chapter uses a separate example module. Chapter 4 starts the shared Users domain with UserId, a type over string.

A const binding cannot change. A record update creates a new record and preserves the old value. Effektive has no assignment, class inheritance, or implicit receiver.

A type declaration over a primitive gives identity to a base value. UserId("u1") creates the value, but it performs no validation. A literal such as "u1" also fits UserId, because a literal has no name of its own. A value of another type needs the constructor. So displayId calls Label(user.id).

A type declaration has identity by name. Two types with identity never mix, even when their bodies are equal. A UserId does not fit a Label. Errors use declaration identity too. Identity prevents accidental substitution.

Two forms stay transparent aliases of their body: a union with a non-literal member, and a bare name such as type Alias = Other. An alias and its body are interchangeable.

A signature names declared types. A primitive type such as string or int can occur only inside a type or error declaration. So this module declares type Label = string and uses Label in signatures.

A record body has identity too, as in type Account = { name: Name }. A record gets a runtime tag only when a union alias of its own module lists it. Any other body, such as string, has no runtime marker. Two values of one numeric type with identity accept comparisons, addition, and subtraction. A literal operand fits the same type, so total * 2 is a Cents when total is a Cents.

An optional field read returns Option<T>. Some(value) represents presence, and None represents absence. This rule prevents an absent field from becoming an unchecked undefined value.

Match expressions require complete coverage. Record unions need a final wildcard if a tag is missing, optional, or open-ended. A tag arm retains every member that can match at runtime. The pattern matching reference shows an overlapping-tag example. Every arm produces a compatible result type. A never branch, such as fail(error), fits any result type.

The int type contains finite safe integers. Addition, subtraction, and multiplication can defect when the result is invalid. Division always returns number.

Records reject missing required fields and unknown fields. A record update evaluates its base once, then evaluates update fields from left to right.

Function contracts

A function contract states its success type, expected failures, and required service methods.

The examples in this chapter use the User, StoreUnavailable, and Users declarations from chapter 4. Chapter 4 defines each shared declaration.

The result type remains Option<User>. A service call performs its operation when the running function reaches the call. The source type never becomes Effect<Option<User>, E, R>.

A declared failure is an expected outcome. A required capability records a call to one service method. A service name in uses expands to every method in that service.

Calls propagate the declared contract of the callee. The declared sets can exceed the body sets, but they cannot omit a body effect.

An exported function closes its contract. An omitted fails clause means no expected failures. An omitted uses clause means no service requirements. The body cannot exceed either set.

A local function can omit its result annotation, its fails clause, and its uses clause. The compiler infers each omitted part from the body. A written clause closes its own set, but a result annotation alone does not. Exported functions require parameter and result annotations. Parameters also require annotations without a contextual function type.

Execution mode is separate from failure and requirement sets. A provider can remove every requirement while the computation remains effectful. Empty sets can therefore describe either execution mode.

Creating an arrow function is pure. Calling that function runs its body each time. Unbodied source function types default to effect execution in version 0.

Nonempty failure or requirement sets imply effect execution. Empty sets do not imply purity. The transpiler must preserve the independently inferred execution mode.

A block returns its final expression. Effektive source has no return statement. Ordered expressions run from left to right, and only the selected branch runs.

One domain, two languages

The Users domain provides the shared declarations for the next four chapters.

Effektive service declarations contain method signatures. Service methods have no this binding. Each method remains a distinct capability after name resolution.

A service method lists only failures from that operation. Method requirement sets are empty. A host provider can have separate acquisition failures and dependencies.

Users.find, Users.save, and Users.all are separate capabilities. A contract can name one method without declaring the other methods. Static tracking does not sandbox host adapters.

The Effect-TS tab represents successful values inside Effect.Effect. Its error parameter contains tagged errors. Its requirement parameter contains the Users service when a function accesses that context.

Later TypeScript examples assume these imports, schemas, errors, and the Users class. Later Effektive examples assume the declarations above. Each Effect-TS tab shows intended translation, not generated output.

Effect-TS tracks the whole Users service in its requirement type. Effektive retains each method requirement in checked IR or backend metadata.

These isolated translations use short error tags and service keys. A transpiler backend must encode resolved identities in tags and keys across modules.

Lookup and update

Small functions keep service operations, domain decisions, and record changes separate.

The first function converts None into a named domain failure. The second function changes a value. The third returns an already active user or activates and saves an inactive one.

getUser is not exported, so the compiler infers its failures and requirements from the body: UserMissing, StoreUnavailable, and Users.find. fail(error) ends the normal path and contributes the error identity. Each error has its own identity, so declarations with equal fields remain different error types.

The match reads the option once and selects one arm. The None arm constructs UserMissing with the requested identifier. StoreUnavailable remains unchanged.

This pair uses 248 non-whitespace characters in Effektive and 304 in Effect-TS, including the pure helper and explicit exported contracts. Shared chapter 4 declarations are excluded from both counts. Effect-TS spells out the Effect.Effect result type, generator, yield*, service-context access and return. Effektive keeps direct calls and a final expression.

Effektive uses one direct call syntax for pure functions and service methods. The checked call still distinguishes an ordinary call from a service operation in typed IR.

Both versions read once and skip the write when the user is already active. Otherwise they activate and save the user. A failure stops the remaining steps; success returns the user.

Pipelines and collections

A pipeline passes its left value as the first argument of each stage.

The runtime evaluates the left side once. It then evaluates the stage callee and explicit arguments. Pipelines associate from left to right.

A stage can name a local function, imported function, builtin, or declared service method. Version 0 excludes placeholders, currying, inline lambda stages, and record-member stages.

The pure helper uses collection operations in both languages. The effectful wrapper uses 96 non-whitespace characters in Effektive and 144 in Effect-TS: a direct pipeline compared with Effect.map and service-context access. Including the helper and explicit exported contracts, the pair uses 187 and 266 characters respectively. Shared chapter 4 declarations are excluded from both counts.

The prelude provides map, filter, and fold. Each builtin traverses from left to right. Map and filter preserve order, while fold carries one accumulator.

Map and filter call their callback once for each visited element. Empty inputs produce empty outputs. Fold returns its initial accumulator for an empty input.

Each callback must be pure and have empty failure and requirement sets. Contextual inline arrows work because the builtin supplies their parameter types. Known pure functions also work.

A callback that provides its own service can still execute effects. Empty failures and requirements do not make that callback pure. Execution mode closes this loophole.

The checker specializes each builtin use to a closed function type before IR serialization. Version 0 does not expose the builtin type variables to users.

Recovery and provision

Effektive controls an operation through explicit syntax and deferred zero-argument functions.

A typed catch handles matching failures from its protected block. Unhandled failures continue to the caller. Catch does not intercept defects or cancellation.

This recovery pair uses 181 non-whitespace characters in Effektive and 216 in Effect-TS, including the Label alias and explicit exported contracts. Shared declarations and saveActive are excluded from both counts. The Effect-TS version uses Effect.as to replace a successful result and Effect.catchTag to recover a missing user. Effektive writes the sequence and typed catch directly; both versions let storage failures continue to the caller.

retry requires a deferred operation. The function below runs its first attempt and allows two more attempts. Each attempt can perform the Users.find operation again.

This retry pair uses 123 non-whitespace characters in Effektive and 156 in Effect-TS, including explicit exported contracts and excluding shared chapter 4 declarations. Effektive passes a deferred direct call. Effect-TS retries the cold effect returned by Users.use; it needs no extra Effect.suspend here. Both allow one initial attempt and two retries.

In Effektive, passing Users.find(id) directly would run the call before retry took control. Effektive never inserts suspension because a parameter expects a deferred function.

Retry preserves the callback result, failures, and requirements. Retry itself has effect execution mode. Its times value must be a finite, nonnegative safe integer literal in version 0.

The host maps its provider registration to users-live.js in the Effect-TS tab. Effektive source keeps the registered host:providers import.

These provider examples assume UsersLive is a Layer<Users> with infallible acquisition and no dependencies. A fallible provider adds its acquisition failures and requirements to the result.

Providing Users removes the Users requirement. The operation still uses effect execution mode. Version 0 receives provider values from typed host modules and defines no layer construction syntax.

Exercise

The zero-argument function defers execution. The controlling builtin can choose when and how often to invoke the operation.

A payment pipeline

The payment workflow composes effectful and pure stages through one data-first pipeline.

The pipeline stops at the first expected failure. chargeOrder retries only the charge call. saveOrder cannot run after a missing order or declined payment.

The uses Orders clause expands to Orders.find and Orders.save. Payments.charge stays method-specific. The resulting contract exposes only the needed service surface.

The charge service can repeat an external action. The application author must decide whether the provider makes repeated charges safe, such as through idempotency.

The Effect-TS tab uses a schema to check safe integers at a boundary. Effektive separately requires its checker and runtime to preserve int arithmetic rules.

The Effect-TS tab uses Effect.gen for ordered operations. Effektive keeps the same order through final-expression blocks and pipeline stages. The source contract presents plain Order as its success type.

Type identity

A type declaration has its own identity, so two types with the same body stay different types.

Each type has identity by name. The union Order lists four record types of this module, so each of them is a tagged record with a runtime tag. Pending and Paid share the fields id and total. The compiler still treats them as different types.

A function that takes a Pending value rejects a Paid value, even where the fields overlap. The compiler reports type-mismatch/003. A record literal is the exception, because it has no name of its own.

Pending({ id, total }) builds a value. A record literal written where exactly Pending is expected also builds it, with no call. A computed record needs Pending(value). A record literal where the union Order is expected is an error, because the literal does not name its state. The spread in reprice keeps the tag and gives a new Pending.

JSON has no tag. Decoding therefore starts at a record type that no union lists, such as OrderInput. A function then builds the Pending value with its constructor.

The Effect-TS panels in this chapter use short tags such as "Pending". The compiler writes module-qualified tags such as "contracts#Pending", so equal names in two modules stay apart.

The match has one arm for each state and no wildcard arm. A missing arm is a compile error (pattern/001). Adding a state to Order shows every match that needs a new arm.

The Effect-TS tab ends with an else branch. TypeScript does not report a missing state there. Effektive does.

A pricing rule can hold other rules. Capped holds one rule, and Sum holds an array of rules. The compiler accepts each cycle because it passes through an array or through a union with members outside the cycle.

The Effect-TS tab spells out the types of the cycle. Each recursive type has an interface and an Encoded mirror interface, and each recursive reference uses Schema.suspend. The form typeof Rule.Type inside a cycle fails the TypeScript check.

The order lifecycle application contains these declarations and more. It has four order states across two modules, match by name, structural decoding, and nine runtime checks.

Exercise

Why does reprice reject a Paid value, although Paid has the fields id and total?

Show the answer

Pending and Paid are different types with identity. Each has its own tag, so the field types do not decide the match.

Core 1 in practice

Scopes supervise concurrent work, schedules shape streams, and Schemas control field presence and service-backed decoding.

These are implemented source forms. The compiler checks the full Effektive example; every Effect-TS tab is checked against Effect 4.0.5.

The child is attached to the scope. When the scoped job ends, Effect interrupts a child that is still running and waits for its cleanup.

The stream stays deferred until consumed. A batch emits when the Sink fills or the schedule fires.

The getter sees missing and present keys. The default runs only for a missing key. Their service requirements belong to decoding; encoding needs neither service in this example.

The encoded record must have a name. Decoding an empty name omits it; encoding an absent name writes an empty string. The getter rejects a missing encoded key before it runs the user transformation.

The scalar Schema accepts a string or safe integer. The name union first tries the service-backed transformation. A Schema issue lets the plain string branch succeed; a successful first transformation wins. Decoding still requires the Validation service. Defects and interruption propagate.

With preserveNull, an absent key stays absent and a present null stays present. With omitNull, null decodes to an absent key. Encoding an absent key omits it in both cases. Explicit undefined fails either Schema.

Both Schemas decode an absent name to Anonymous. OmittedDefault encodes any valid name as an absent key, including names other than Anonymous. PassedDefault writes the name. Omitting the third argument also selects passthrough. Omission skips the wrapped encoder while retaining its static service requirements.

Both readers produce { name: "Anonymous" }. A present string skips the default, while explicit undefined fails. Encoding writes the name; the same omit option can leave it absent. Defaults may use decode services and run for each missing-or-null decode. The wrapped Schema must exclude null in both directions.

An absent score supplies the text "41" to Wire.parse. Present text uses the same parser and skips the default. Encoding calls Wire.print and validates its output before omitting the field, so encoder failures still propagate. This differs from decoded-default omission, which skips the wrapped encoder. Without the omit option, the encoded text is written.

makeScore accepts an absent score and fills it with 4 before schemaMake validates the decoded record. The Schema still requires score for both decoded and wire data. Type-side construction returns SchemaIssue and runs neither wire decoder nor encoder. Defaults in this example belong to the factory. The next example attaches constructor-default metadata to a reusable Schema.

constructDefaults accepts {} and constructs { settings: { score: 4 } }. The fifth Schema parameter records that make-input shape; decoded and wire records still require both fields. Arrays retain the element make input, so constructorDefaultsList accepts [{}] during construction. These defaults run only when making values. Optional field adapters retain their nested make inputs, as the next example shows. Guarded recursive constructor inputs are shown below.

constructSettings({ settings: {} }) constructs { settings: { score: 4 } }. Decoding {} instead uses the wire default { settings: { score: 8 } }. A wire default leaves settings required during construction. optionalSettings permits an absent settings key during construction and fills the nested score when settings is present. Null is a wire-only missing-value policy. Optional transformations use their target’s make input; Option-valued fields require None or Some containing complete decoded data.

constructTree({ children: [{}] }) constructs { score: 4, children: [{ score: 4, children: [] }] }. Each self reference retains TreeInput, so defaults work at every nested node. Decoded and wire trees still require score and children. Arrays guard this recursion; optional keys and tagged unions with terminal branches are also supported. Constructor wrappers preserve a guard, and their callbacks cannot capture self. The next example gives the same recursive tree a separate wire representation.

readWireTree converts text scores to integers at every node using Wire.parse. writeWireTree walks the same decoded tree and returns text scores using Wire.print. constructWireTree({ children: [{}] }) produces integer scores with defaults and needs neither wire service. Each self reference retains all three types: complete decoded Tree, complete encoded WireTree, and partial TreeInput. Optional-key and tagged recursive forms can also keep distinct wire types. The next example attaches constructor defaults to fields that already have wire-presence rules.

makeDualDefaults({}) constructs { score: 4 }, while decoding {} through dualDefaultScores produces { score: 8 }. The field remains required in decoded data and optional in wire and make inputs. optionalDefaultScores keeps score optional in both decoded and wire data: decoding {} leaves it absent, while construction supplies 4. The combined descriptor types retain presence and constructor metadata across annotations and imports. The next example applies a field adapter after the constructor default and shows which metadata it keeps.

makeAdapterAfterDefault({}) still constructs { score: 4 }; decoding {} uses 8. Unary presence and wire-default adapters retain the constructor default in either order. Optional bridges take defaults only from their decoded target. The Option adapter resets the inherited default: makeAdaptedOption requires score: None or score: Some(value), and an absent score is an error. A new Option constructor default can be attached after that reset. The next example carries recursive self through wire-default adapters.

makeDefaultedTree({ children: [{}] }) fills each score with 4 and supplies empty children at the leaf. readDefaultedTree({ score: 1 }) uses the wire default and returns { score: 1, children: [{ score: 8, children: [] }] }. The array guards self through the default adapters. Null-as-missing also guards optional recursive links. Optional bridges retain guards from their Schema arguments; defaults and getters cannot capture self.

Modules and typed IR

Modules expose named declarations and keep host integration behind typed interfaces.

Version 0 permits named imports from relative .eff files and registered host modules. It excludes default imports, namespace imports, renaming, re-exports, and package resolution.

Module constants require pure initializers. Imports cannot run application service operations. A host starts execution through an entry function after it supplies required providers.

The transpiler parses source, resolves identities, infers effects, checks contracts, specializes builtins, and emits typed IR. Its Effect-TS backend emits TypeScript from checked IR.

Resolution assigns stable identities to types, errors, services, capabilities, values, and locals. Equal names in different modules do not identify the same declaration.

The IR resolves every reference to a stable identity. It separates ordinary calls from service operations. It preserves retry, provide, catch, constructions of types with identity, and source positions as explicit nodes.

A pipeline needs no IR node. Lowering creates fresh bindings and ordinary call or service-operation nodes. This preserves single evaluation, stage order, and useful diagnostic positions.

Acceptance fixtures must cover evaluation order, branch selection, failure propagation, contract rejection, closure deferral, retry, and provider resolution. Pipeline fixtures must also check stage identity.

The application acceptance rule now guides further additions. The target covers a service workflow, a scheduled worker, and a stream processor. Each must retain precise contracts and pass failure, cancellation, and cleanup checks. All three gates now pass using existing forms. Application orchestration stays in Effektive; typed host adapters supply drivers and the runtime entry point. Broader package interoperability, gap item 9, remains deferred.

The native reference compares the selected policy with Effect repetition and retry. The accepted language stopping rule is satisfied.

The runnable service workflow also uses existing forms. Its Service workflow source validates requests, checks business rules, obtains a price and retries transient writes. The registered SQL adapter supplies one atomic save with receipt validation and connection release. Fifteen Service workflow runtime checks cover transactions, failures, retry timing and replay, and cancellation. Body interruption awaits rollback and release. After COMMIT starts, cancellation can preserve a committed row. The recording driver performs no external I/O.

The runnable stream processor keeps the complete pipeline in Stream processor source. It transforms live input with concurrency two, preserves order, applies selected fallbacks and writes batches under backpressure. Thirteen Stream processor runtime checks cover success, failures, replay and awaited shutdown. Native transduction can emit a partial batch before input failure. Typed recovery follows native mixed-cause limits. The recording driver performs no external I/O. The accepted stopping rule selects no further automatic API additions; release acceptance remains separate work. The remaining and deferred gap record lists open APIs, item 9 and runtime evidence limits.

The runnable order lifecycle is a witness for type identity. It is not a gate application. Its source in contracts.eff and orders.eff declares four tagged states across two modules, matches them by name, and prices a recursive rule tree. It decodes JSON through an untagged record type. Nine Order lifecycle runtime checks cover each transition, the InvalidTransition failure, pricing, decoding and the encoded tag.

Separate release checks now cover editor references, rename, completion, semantic tokens and contract quick fixes, a bundled local CLI and VSIX, and installed editor startup, save and restart. The playground passed automated keyboard and error-recovery checks at 375, 720 and 1280 pixels. The service workflow has seven real loopback HTTP and SQLite checks for persistence, failures, rollback, cancellation and connection close. Full M1/M3/M4 release measurements meet the existing 100 ms p90 diagnostics budget on the large synthetic project and include 10,000 distinct edits across three open documents. These finite memory observations establish no bound. The user’s manual editor and playground acceptance remains pending. These additions change no source forms or package-interoperability deferral.
