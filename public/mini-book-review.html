What Effektive is

Effektive is a small functional language that compiles to Effect-TS.

Effektive combines immutable data, arrow functions, pattern matching, and typed services. Direct calls carry failures and required capabilities.

A contract with result A, failures E, and requirements R becomes Effect.Effect<A, E, R>.

Services become Context services; providers become Layer values. Records, types with identity, and errors become Schema declarations; options become Option values.

Effect-TS moduleRole in transpiled code
effect: Effect, Context, Layer, Option, SchemaComputations, services, providers, options, records, types with identity, and errors used in these examples.
effect/http, FileSystem, and @effect/platform-node, -bun, or -browserHTTP, files, and host runtimes.
effect/sql and a driver such as @effect/sql-pgDatabase services.
@effect/opentelemetryExport of traces, metrics, and logs.

Version 0 specifies the core mapping. HTTP, file, SQL, and telemetry bindings need later specifications. Typed host modules will expose these bindings as services.

The compiler repository contains the Deno transpiler and command-line tool (CLI). This book uses handwritten translations for Effect 4.1.2, the TypeScript library. The site does not execute Effektive.

The compiler requires Deno 2.9.8. Clone the repository, check the tutorial, then build its TypeScript.

The first --tsc build downloads dependencies. See the tutorial and CLI and VS Code installation guide.

The transpiler emits a typed intermediate representation (IR): expression types, execution modes, failures, requirements, and source positions. The backend translates checked IR into TypeScript.

Implemented core 1 subsetLater or deferred
Immutable records, options, type identity, and concrete refinementsMacros and general recursive schemas
Functions, inferred inputs, pipelines, match, and typed catchUser generics and abstract predicates
Services, retry, repetition, schedules, providers, and modulesArbitrary JavaScript and Promise interoperation
Scoped operation records, references, races, fibers, and traversalFull Scope parity and general concurrency APIs
Incremental and buffered streams and sinksGeneral Stream and Sink APIs

Typed catch handles declared domain failures, such as a missing user. It excludes defects and cancellation. Invalid safe-integer arithmetic is a defect.

Calls propagate failures and service requirements. Execution mode records whether a call performs effects.

Values and types

Bindings and aggregate values are immutable.

This module is separate from the shared Users domain in chapter 4, which defines string-based UserId.

A record update creates a new value. Effektive has no assignment, class inheritance, or implicit receiver.

UserId("u1") constructs without validation. Unnamed literals such as "u1" also fit. Other named types require conversion: Label(user.id).

Type and error declarations have identity by name, even with identical bodies. UserId and Label are distinct.

Unions with non-literal members and bare names such as type Alias = Other are transparent aliases, interchangeable with their bodies.

Signatures use declared types. Primitives such as string and int occur only inside type or error declarations: type Label = string.

Record declarations have identity: type Account = { name: Name }. A record receives a runtime tag when a union alias in its module lists it. Other bodies, including string, have no runtime marker.

Values of the same numeric type with identity support comparisons, addition, and subtraction. Literal operands fit: total * 2 remains Cents when total is Cents.

An optional field read returns Option<T>: Some(value) or None, never unchecked undefined.

Match requires complete coverage and compatible results. Record unions need a final wildcard for missing, optional, or open-ended tags. Each arm retains all members that can match at runtime; see overlapping tags. A never branch such as fail(error) fits any result type.

The int type contains finite safe integers. Invalid addition, subtraction, or multiplication causes a defect. Division returns number.

Records reject missing required fields and unknown fields. Updates evaluate the base once, then update fields from left to right.

Function contracts

A function contract records its result, expected failures, and required service methods.

These examples use User, StoreUnavailable, and Users from chapter 4, with the header imports Users from "./users-service.eff".

Service calls execute when reached. The source result stays Option<User>; the transpiler adds the Effect wrapper.

A failure names an expected outcome; a capability names a service method. A with clause naming a service includes all its methods.

Calls propagate the callee's declared contract. Declared sets may exceed body effects but cannot omit them.

The compiler infers omitted fails clauses. A written fails clause bounds the allowed failures.

Service headers permit requirement inference and bound the external services a module can require.

Without service headers, an exported function that omits with cannot require services.

Local functions infer omitted results, parameter types, failures, and requirements from their bodies.

Explicit unknown and omitted input annotations infer alike. An operator alone cannot determine an input type.

Exports require result annotations. New inferred failures reach host TypeScript without diagnostics. Written fails clauses prevent this; inlay hints show inferred failures.

Inferred exported inputs validate unknown data inside the Effect.

Validation adds SchemaError to inferred failures; written fails clauses must include it. Interfaces without bodies retain unknown for omitted inputs.

Execution mode is independent of failures and requirements. Provision can remove every requirement while execution remains effectful.

Arrow creation is pure; calls run the body each time. Source function types without bodies default to effect execution in version 0.

Nonempty failure or requirement sets imply effects. Empty sets permit either execution mode, which the transpiler must preserve.

A block returns its final expression; Effektive has no return statement. Expressions run from left to right. Only the selected branch runs.

One domain, two languages

The next four chapters share the Users contract.

Service methods have no this binding. Each resolved method remains a distinct capability.

Each method lists its own failures and has no requirements. A host provider may add acquisition failures and dependencies.

A contract can require Users.find without Users.save or Users.all. This static tracking does not sandbox host adapters.

Effect.Effect records the result, tagged errors, and Users when a function accesses that service context.

Later TypeScript examples share these declarations. Effektive uses a service header plus an ordinary import.

Effect-TS tabs are illustrations, not generated output.

Effect-TS tracks the whole Users service. Effektive retains individual method requirements in checked IR or backend metadata.

Error tags and the service key use users-service identities; equal names in different modules remain distinct.

Lookup and update

Separate service calls, domain decisions, and record updates.

getUser converts None to a domain failure. activate updates a value. saveActive activates and saves only inactive users.

The compiler infers UserMissing, StoreUnavailable, and Users.find for local getUser. fail(error) ends normal execution and adds the error identity. Equal error fields do not imply equal types.

Match reads the option once. None constructs UserMissing with the requested identifier; StoreUnavailable propagates unchanged.

Characters without whitespace: Effektive 223; Effect-TS 304, including the helper and explicit export contracts, excluding chapter 4 declarations. Effect-TS adds the wrapper, generator, yield*, context access, and return.

Pure calls and service calls share syntax. Typed IR distinguishes them.

Both read once, skip writes for active users, otherwise activate and save. Success returns the user; failure stops subsequent steps.

Pipelines and collections

A pipeline passes its left value as the first argument to each stage.

Stages associate left to right. Evaluation reads the initial value once, then each stage callee and its explicit arguments.

Stages can name local functions, imports, builtins, or service methods. Version 0 excludes placeholders, currying, inline lambdas, and record-member stages.

Both pure helpers use collection operations. Characters without whitespace: wrappers 83/144; with helpers and explicit export contracts, 174/266 (Effektive/Effect-TS). Counts exclude chapter 4 declarations. Effect-TS uses Effect.map and context access.

map, filter, and fold traverse left to right. Map and filter preserve order; fold carries an accumulator.

Map and filter call callbacks once per visited element; empty inputs produce empty outputs. Empty folds return the initial accumulator.

Callbacks require pure execution and empty failure and requirement sets. Builtins supply inline-arrow parameter types. Known pure functions also work.

A callback that provides its own service can still perform effects. Empty failure and requirement sets do not establish purity.

The checker specializes builtins to closed function types before IR serialization. Users cannot access builtin type variables in version 0.

Recovery and provision

Control forms use explicit syntax and deferred zero-argument functions.

Typed catch handles matching failures from its block. Other failures propagate. Defects and cancellation bypass catch.

Characters without whitespace: Effektive 156; Effect-TS 230, including Label and explicit export contracts, excluding shared declarations and saveActive. Effect-TS uses Effect.as and Effect.catchTag for success and UserMissing recovery. Both propagate storage failures.

retry takes a deferred operation. This policy allows an initial Users.find call and two retries.

Characters without whitespace: Effektive 109; Effect-TS 156, including explicit export contracts, excluding chapter 4 declarations. Effektive defers the call. Effect-TS retries the cold Users.use effect without Effect.suspend.

Passing Users.find(id) directly executes before retry gains control. A deferred parameter never causes automatic suspension.

Retry preserves results, failures, and requirements; retry itself is effectful. times requires a finite, nonnegative safe integer literal. schedule, while, and until select policies. General Schedules may add failures and requirements.

The Effect-TS tab maps the registered host provider to users-live.ts. Effektive imports host:providers.

Here, UsersLive: Layer<Users> has infallible acquisition and no dependencies. Fallible providers add acquisition failures and requirements.

Provision removes Users requirements, retaining effect execution. Host modules supply providers; layer constructs them in source.

A payment pipeline

The payment pipeline combines pure and effectful stages.

Failure stops the pipeline. chargeOrder retries only the charge. Missing orders and declined payments prevent saveOrder.

The compiler infers Orders.find, Orders.save, Payments.charge, OrderNotFound, and PaymentDeclined. Both service headers permit the requirements.

Retry can repeat an external charge. The author must assess whether the provider makes repetition safe, for example through idempotency.

Effect-TS validates safe integers at the schema boundary. The Effektive checker and runtime must preserve int arithmetic rules.

Effect-TS orders operations with Effect.gen; Effektive uses blocks and pipeline stages. The source result is Order.

Type identity

Type declarations remain distinct even with identical bodies.

A where clause adds a concrete predicate. The compiler proves known values and emits an Effect Schema check.

The inferred closed input is { amount: Positive }. The export checks required fields, unknown fields, and Positive.

Validation runs inside the Effect before the body and may fail with SchemaError. It performs no coercion or defaulting.

Predicates support integer comparisons, +, -, &&, ||, required fields, and string or array length. String length counts UTF-16 code units.

Floating-point guards provide no integer proofs. Unknown inputs receive runtime record-predicate checks at checked entries.

This release excludes floating-point predicates, arbitrary calls, generics, and abstract predicates.

Host interfaces expose unrefined data. They cannot declare refinements or reference refined contracts, including imported types and services from host providers.

Order lists four record types from its module, giving each a runtime tag. Pending and Paid remain distinct despite sharing id and total.

A Pending parameter rejects Paid with type-mismatch/003. An unnamed record literal is an exception.

Pending({ id, total }) constructs Pending. Literals also work where exactly Pending is expected; computed records require Pending(value). A literal at Order is an error: it names no state. The spread in reprice preserves the tag in a new Pending.

JSON has no tag. Decode into an untagged record such as OrderInput, then construct Pending.

These panels shorten tags to "Pending". Generated tags qualify the module, such as "contracts#Pending", keeping equal names distinct.

Match covers every state without a wildcard. A missing arm causes pattern/001; adding a state identifies every incomplete match.

The Effect-TS else branch hides missing states from TypeScript. Effektive reports them.

Capped holds one rule; Sum holds an array. The compiler accepts cycles through arrays or unions with members outside the cycle.

Each recursive Effect-TS type needs an interface and Encoded mirror. References use Schema.suspend; typeof Rule.Type fails checking inside a cycle.

The order lifecycle includes four states across two modules, matching by name, structural decoding, and nine runtime checks.

Core 1 in practice

Scopes supervise concurrent work. Schedules control streams. Schemas govern field presence and decoding through services.

The compiler checks the full Effektive example. Effect-TS tabs pass checks against Effect 4.1.2.

The scope owns the child. At job completion, Effect interrupts running children and awaits cleanup.

The stream runs when consumed. Batches emit when the Sink fills; stream completion emits any partial batch.

Getters handle missing and present keys; defaults handle missing keys only. Decoding requires their services; encoding requires neither here.

Encoded name is required. Empty text decodes to absence; absence encodes to empty text. Missing encoded keys fail before user transformation.

The scalar accepts strings or safe integers. The name union tries the service transformation first; Schema issues permit string fallback. First success wins. Decoding requires Validation; defects and interruption propagate.

preserveNull retains null; omitNull decodes null to absence. Both preserve absent keys and omit absent values during encoding. Both reject explicit undefined.

Absent names decode to Anonymous. OmittedDefault omits every valid name during encoding; PassedDefault writes it. No third argument means passthrough. Omission skips the encoder but retains static service requirements.

Both readers produce { name: "Anonymous" }. Present strings skip defaults; explicit undefined fails. Encoding writes name unless omit is selected. Each missing-or-null decode runs the default, which may require services. The wrapped Schema must exclude null in both directions.

Absent score supplies "41" to Wire.parse; present text skips the default. Encoding runs Wire.print and validates output before omission, retaining encoder failures. Decoded-default omission skips the encoder. Without omit, encoding writes the text.

makeScore defaults score to 4 before schemaMake validation. Decoded and wire data require score. Construction may fail with SchemaIssue; neither wire decoder nor encoder runs. These defaults belong to the factory.

constructDefaults({}) builds { settings: { score: 4 } }. Schema parameter five records make input; decoded and wire records require both fields. Arrays retain element make inputs, so constructorDefaultsList accepts [{}]. Defaults run during construction only.

constructSettings({ settings: {} }) fills score with 4. Decoding {} defaults settings to { score: 8 }. Wire defaults leave settings required for construction. optionalSettings permits absence, filling score when settings is present.

Null means missing only on the wire. Optional transformations use target make inputs. Option fields require None or Some with complete decoded data.

constructTree({ children: [{}] }) builds { score: 4, children: [{ score: 4, children: [] }] }. self retains TreeInput for recursive defaults; decoded and wire nodes require both fields. Arrays, optional keys, and tagged unions with terminal branches guard recursion. Constructor wrappers preserve guards; callbacks cannot capture self.

At each node, readWireTree uses Wire.parse and writeWireTree uses Wire.print. constructWireTree({ children: [{}] }) supplies integer defaults without wire services. self retains decoded Tree, encoded WireTree, and partial TreeInput. Optional-key and tagged recursion also support distinct wire types.

makeDualDefaults({}) builds { score: 4 }; dualDefaultScores decodes {} to { score: 8 }. Decoded data requires score; wire and make inputs permit absence. optionalDefaultScores permits decoded and wire absence: decoding preserves absence, construction supplies 4. Descriptors retain presence and constructor metadata across annotations and imports.

makeAdapterAfterDefault({}) builds { score: 4 }; decoding {} supplies score 8. Unary presence and wire-default adapters preserve constructor defaults in either order. Optional bridges inherit defaults from decoded targets only. Option resets inherited defaults: makeAdaptedOption requires score: None or score: Some(value). An Option constructor default may follow the reset.

makeDefaultedTree({ children: [{}] }) supplies score 4 and empty arrays for leaf children. readDefaultedTree({ score: 1 }) uses the wire default: { score: 1, children: [{ score: 8, children: [] }] }. Arrays preserve guards through default adapters; null-as-missing guards optional recursive links. Optional bridges retain Schema guards; defaults and getters cannot capture self.

Modules and typed IR

Modules export named declarations. Typed interfaces define host integration.

A service header imports a contract by explicit path. Headers precede ordinary imports and declarations.

Headers bound external requirements from calls and produced output contracts. Ordinary imports grant no service allowance.

The bound includes deferred values stored or passed to functions, even when the result is void.

Input types alone need no header. Forwarding inputs and identity updates preserve this exemption.

Provision around a write does not supply the stored computation. Provision inside that computation can remove its service requirement.

With service headers, all functions infer omitted with clauses. Written clauses remain optional upper bounds.

Version 0 permits named imports from relative .eff files and registered host modules. It excludes default imports, namespaces, renaming, re-exports, and package resolution.

Module constants require pure initializers. Imports cannot execute service operations. The host supplies providers, then calls an entry function.

The transpiler parses, resolves identities, infers inputs and effects, checks contracts, specializes builtins, and emits typed IR.

IR version 7 records predicates, checked input contracts, entry validation, and proof certificates. The backend emits TypeScript from checked IR.

Types, errors, services, capabilities, values, and locals receive stable identities. Equal names in separate modules remain distinct.

IR references stable identities and distinguishes ordinary calls from service operations. Nodes preserve retry, provide, catch, identity constructors, and source positions.

Pipeline lowering creates fresh bindings and call or service-operation nodes, preserving single evaluation, stage order, and diagnostic positions.

Acceptance fixtures must cover evaluation order, branches, failures, contract rejection, closure deferral, retry, and provider resolution. Pipeline fixtures must also check stage identity.
